# Workflow

- Reads reference documentation before implementing an unfamiliar integration. Confidence: 0.8
- Delivers incrementally with tight scope ("don't boil the ocean"); ships the smallest live slice first and measures before expanding. Confidence: 0.9
- Uses feature flags with a safe fallback to existing behavior, and logs when the feature is off or degraded. Confidence: 0.85
- Prefers feature flags to default to enabled (opt-out) rather than disabled (opt-in), with graceful fallback when the required credential/key is absent. Confidence: 0.7
- Treats changes to criteria/policy as product changes: version them and re-evaluate against a frozen eval set. Confidence: 0.8
- Values explicit non-goals and acceptance criteria to bound scope and define "done". Confidence: 0.8
- Keeps diffs strictly scoped to the task: does not reformat unrelated lint debt and does not "fix" pre-existing test failures unless they block the task at hand. Confidence: 0.85
- Wants a shippable end-to-end product path a person can actually run (one command or one API call producing a real result) rather than another design pass; distinguishes "product path, not just pytest". Confidence: 0.8
- When resuming prior work, checks the previous status/report's claims against the actual code and reports what was wrong, missing, or newly true, rather than restating them. Confidence: 0.75
- Does not assume US English: the product's users are often Nigeria/West Africa (pidgin/Naija English, Yoruba, Igbo, Hausa). Confidence: 0.8
- Uses VS Code with Pylance and expects editor type-checking (Pylance/pyright) to resolve against the project's uv `.venv`, not just CLI checks passing. Confidence: 0.7
- Reports honestly and without congratulation: never fabricates answers or metrics; stops and reports missing prerequisites (e.g. an API key) rather than inventing results; calls mediocre work mediocre. Confidence: 0.85
- Distinguishes BLOCKED (missing product policy requiring a human decision) from FAIL (wrong behavior) and names the decision a human must make. Confidence: 0.75
- Requires an explicit ship/hold decision per area against a quantified bar (e.g. >=90% pass rate and zero misses on safety-critical cases). Confidence: 0.75
- Reports top failures grouped by failure mode, each with product impact and a recommended fix (catalog/threshold/code). Confidence: 0.7
- Sets a quantified completion target (e.g. 99% success rate) and iterates fix → full-suite rerun until it is met, rather than stopping at "no obvious errors". Confidence: 0.7
- Bounds iteration on a fix: after the first full pass, at most one more criteria/threshold tweak and one more full rerun, then stop. Confidence: 0.7
- Wants the domain rules specified as a reviewable artifact before code: a rule table of trigger / action / kill-condition plus the decision tree and schema, then implementation as a transcription of those rules. Explicitly "do not start with prompt poetry" — research outputs before code. Confidence: 0.85
- Rejects US-centric defaults: advice and product rules must be adapted to the user's country, currency, inflation, and tax wrapper rather than imported unchanged (a US 401(k)/Roth rule is invalid for a Lagos cash earner). Confidence: 0.8
- Before implementing a new spec, first maps what already exists: reports which existing modules map to the spec and which are missing, then reuses that infrastructure rather than merging into or duplicating it. Confidence: 0.8
- Defines "done" as the capability being live and the old path structurally unable to do it: refuses new feature work until the built thing is wired into real traffic ("stop adding features, wire live traffic to X"), treats a module nothing calls as unfinished, and states the bar as the forbidden end state ("if the old path can still call a rail, the PR is not done"). Confidence: 0.8
- Before flipping a routing/ownership change, dual-runs it: replays recorded production traffic through both the old and the new path, compares actual side effects (did money move, how much, out of which bucket), requires zero unexpected movements on the new path, and only then flips the flag. Confidence: 0.8
- Removes dead/unreachable code outright rather than wrapping, deprecating, or leaving it: "delete the dead policy, do not wrap it" — when a module's rules have become unreachable, deletes them and shrinks or splits the file, rather than leaving an unreachable allowlist or facade behind. Confidence: 0.9
- Scopes a removal-focused PR as "delete-and-lock": adds no features and makes no opportunistic improvements to adjacent systems (explicitly "do not add features. do not improve Voice"). Confidence: 0.85
- After deleting a capability, sweeps the whole repo for every one of its names/identifiers and requires each remaining hit to be a delete, a comment explaining the absence, or a test asserting absence — no stale references and no lingering references in docs, comments, or config. Confidence: 0.85
- Answers "can it still do X?" by proving it against the real code path: runs a scratch demonstration through the actual policy/rail/orchestrator and reports the observed output (what was called, the receipt, the decision mode) rather than answering from memory or docs. Confidence: 0.7
- When judging whether a capability works, separates "the mechanism exists and is proven" from "the real deployment has the data/credentials/plumbing it needs", and names the missing prerequisite (e.g. an un-synced ledger or absent API key) as the next thing to build. Confidence: 0.7
- Splits multi-part work into separate, independently reviewable PRs — one concern per branch/commit, each with its own tests and a green suite — rather than a single combined change. Confidence: 0.75
- Scopes a deletion surgically to the affected path and deliberately preserves same-named functionality that other consumers still use (e.g. delete the delegated path's OTP flow but keep the in-app and simulation equivalents). Confidence: 0.8
- Gates a capability that leans on a not-yet-proven data source behind the conservative default (no unattended action) until the feeding change has been correct in production; the safe hold is the shipped default. Confidence: 0.75
- Before calling parallel/overlapping branches done, verifies their combined merged state rather than trusting each branch green in isolation: merges them onto a throwaway branch off main, runs the build and full suite on the result, confirms both features survive together, then deletes the scratch branch. Confidence: 0.7
- Distinguishes code-committed from code-shipped: reports the exact branch/commit topology (local branches, whether `main` is untouched, nothing pushed/merged/deployed) and says plainly that "the repository has the updated code; the running service does not". Confidence: 0.7
