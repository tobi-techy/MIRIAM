# Architecture

- Separates decision logic from language generation: typed/structured layers own the judgments code branches on; the LLM stays responsible for user-facing text. Confidence: 0.9
- Composes decisions in code (if-statements over typed scores) rather than prompting a model to weigh multiple factors and decide. Confidence: 0.9
- Keeps individual questions atomic and independent; avoids chaining reasoning across questions or assuming one answer is visible to another. Confidence: 0.85
- Distinguishes fail-closed (safety-critical: block on error) from fail-open (only with a documented fallback). Confidence: 0.85
- Avoids duplicating policy in two places; prefers a single source of truth and deleting superseded instructions. Explicitly wants exactly one public entrypoint per capability ("if two entrypoints exist, kill one"), forbids starting a parallel/duplicate module — extend the existing package and say so when the placement is uncertain — and insists the superseded writer be deleted or disabled rather than kept alongside the new one ("do not keep both writers"). Confidence: 0.9
- Never guesses an identifier or value that must come from a real external source (e.g. an onchain asset ID): resolve it from a live source or refuse outright, because a plausible-but-wrong value is more dangerous than an error. Confidence: 0.85
- For hand-entered external reference data (rates, inflation, thresholds), dates every row and labels it sourced vs PLACEHOLDER so a guess cannot read as official, and treats a table past its staleness window as unknown (fails closed) rather than producing a confident answer from stale figures. Confidence: 0.8
- Treats a bare confirmation ("do it", "go", "yes") as executing exactly the previously proposed action and nothing beyond it. Confidence: 0.75
- Trims context/state sent to models: no embeddings, raw tool dumps, or entire documents; only the relevant slice. Confidence: 0.8
- Evaluates decision gates in a fixed, documented precedence order (block/escalate before clarify/planning) so safety checks are never masked by lower-priority checks like clarify or relevance. Confidence: 0.8
- Represents missing inputs as absent rather than zero, labels every assumption explicitly, and lowers a confidence score instead of inventing a plausible number. Confidence: 0.8
- Keeps the agent out of irreversible or money-moving actions: it recommends, validates, and prepares a draft, while execution and enrollment stay user-signed and owned by a separate authority. Confidence: 0.75
- Never lets an LLM cause a side effect: money movement is deterministic code with zero write methods on the model/narration side, and "if the LLM can cause a side effect by emitting text, the design is wrong — stop and fix it." No tool named send_money/transfer/unlock/invest may exist on a model. Confidence: 0.95
- Enforces strict isolation between the execution, judgment, and language layers as separate modules that must not be merged; each layer owns exactly one job and reads/returns a single shared state object. Confidence: 0.85
- Makes a machine-built state object the single source of truth that the LLM may read, and grounds every figure the model emits to a value already present in that state — an invented number is refused (clamped) rather than shown. The model never does arithmetic. Confidence: 0.85
- Requires structured, id-bound confirmations: a confirmation is a token bound to one exact proposed action (amount, counterparty), and a chat word like "yes" is never parsed as consent (the client sends `{confirm_id, yes|no}`, and free-text "yes" settles nothing). Confidence: 0.9
- Gives every money or repeated mutation an idempotency key, preconditions, a limit check, and an audit row recording before/after balances and the decision id. Confidence: 0.85
- Treats a confirmation only as authorizing exactly the staged action (from the stored token) and makes it non-replayable; a replayed or unknown confirm id is refused. Confidence: 0.8
- Routes each live request to exactly one owner using deterministic code (a classifier, never a model call) before any downstream work runs: money turns go to the ledger-backed orchestrator, everything else to the read-only agent. Confidence: 0.75
- Treats authoritative money events as integrations with the system of record: an inflow arrives from the rail/webhook carrying its own payment id as the idempotency key, never from a chat message, which is for instructions and narration only. Confidence: 0.75
- On shared-store failure, returns a typed failure the user can be told (a fixed, quotable line like "I could not complete that. Try again.") rather than silently substituting local/process state that can diverge across workers; any degradation to a fallback must be gated behind an explicit flag that is safe for the deployment topology and defaults off (multi-worker). Confidence: 0.8
- Orders writes source-first: the system of record commits the state change and only then runs any downstream projection/notification ("Go credits first"); the report is a projection of a committed change, never its source. Confidence: 0.8
- Attaches a side effect at the specific event site, never to a shared helper that also serves inverse operations — e.g. not on a credit helper that is reused for rollback/cancel/expiry, which would misreport reversals as income. Confidence: 0.8
- Centralizes an eligibility/skip guard in the boundary component (the client skips a currency the store cannot represent) so call sites cannot forget it; a value the target store cannot express is skipped and logged, never partially written. Confidence: 0.7
- Rejects invalid caller input at the API boundary as a client error (HTTP 4xx) instead of letting it surface as a generic 5xx, because a 5xx tells an upstream rail the server failed and invites a retry of a payload that can never succeed; validates the parsed value's semantics (finite, positive), not just whether the parser raised. Confidence: 0.8
